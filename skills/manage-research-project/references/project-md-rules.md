# PROJECT.md rules

## 用途

PROJECT.md 是一个项目每天都能查看的推进表。它要让用户迅速知道：

- 这个课题要解决什么科学问题；
- 01–05 分别推进到哪里；
- 现在具体在做哪些事情；
- 每项真实任务已经做了什么、下一步做什么、卡在哪里；
- 哪些事情已经完成；
- 哪些事情做过但后来被取消，避免以后重复开展。

它不是科研笔记、实验设计正文、分析报告、图片规划正文或论文正文。不要把其他模块的完整内容复制进来，也不要替负责这些工作的 skill 做科学判断。

## 模板和实际文件

assets/PROJECT.template.md 是完整结构模板，用来规定 PROJECT.md 最终可以长成什么样。实际项目中的 PROJECT.md 不应机械复制整份模板。

新项目先建立真实骨架，后续随着讨论和工作推进逐渐补充：

- 始终保留项目名称、课题目标、目前主要做到、现在在做和最近更新时间；
- 始终保留 01–05 五个大标题、状态说明和取消 / 废弃记录；
- 01 和 02 使用模板中的固定小标题；
- 03 只为已经存在的真实分析任务建立任务块；
- 04 只为已经存在的真实 Fig 或图片建立任务块；
- 05 保留投前论文成稿、期刊适配、审稿修回三个固定部分，但只展开当前确实存在的稿件、材料和审稿意见；
- 没有真实任务时，用“暂无已登记的分析任务”“暂无已登记的图片任务”或其他真实短句说明，不建立示例任务；
- 不把尖括号占位符、示例任务、示例 Fig、虚构路径或未经确认的内容写入实际项目。

未知信息用接地气的真实表述，例如“还没定”“还没有”“无”或“尚未进入审稿”。不要为了填满模板而推测。

## 顶部信息

- 课题目标：说明这个项目真正要解决的科学问题。只能使用用户、项目文件或负责该部分的 skill 已经确认的内容。
- 目前主要做到：写当前实际推进到的 01–05 部分；并行时可以列多个。
- 现在在做：汇总所有状态为“进行中”的具体事项，使用分号隔开；没有则写“无”。
- 最近更新时间：每次经过用户批准更新 PROJECT.md 后刷新。

顶部只是快速入口，不再增加“全流程总览”“当前步骤”“下次要做”“下一阶段”或 Git 只读基线。

## 固定结构

### 01_立项与选题论证

固定使用：

- 发现问题 / 找 gap；
- 提出科学假设；
- 文献支撑与创新点；
- 可行性评估；
- 预期结果与意义。

每项只记录状态、还缺什么、详情文件和下一步。不要在 PROJECT.md 重新写一份完整的立项论证。

根目录 01_立项与选题论证.md 即使已经作为空占位文件存在，也不能据此判断任何小项已经开始或完成。状态必须来自实质内容或已确认信息。

### 02_实验设计

固定使用：

- 故事层；
- 证据层；
- 展示层；
- 数据层；
- 技术路线层。

每项只记录状态、还缺什么、详情文件和下一步。不要复制完整实验设计，也不要自行补充分组、重复、处理、采样或技术参数。

根目录 02_实验设计.md 即使已经作为空占位文件存在，也不能据此判断任何层级已经开始或完成。状态必须来自实质内容或已确认信息。

### 03_数据与分析

每项真实分析是一个同级任务块。无论待办、进行中、待审计、已完成还是取消，都保留在同一任务序列中，不建立“正在做”“已完成”等状态分区。

每个任务按实际情况记录：

- 使用的数据；
- 已经做了什么；
- 现在做到；
- 下一步；
- 卡在哪里；
- 当前结果；
- 最近更新。

已完成任务不挪位置。它的标题状态改为“已完成”，下一步可以写“无”。

### 04_结果主库

每个真实 Fig 或图片是一个同级任务块。无论状态如何，都保留在同一任务序列中，不建立“正在做”“已定稿”等状态分区。

每个任务按实际情况记录：

- 这张图要说明什么；
- 用的是哪项分析；
- 现在做到；
- 下一步；
- 卡在哪里；
- 当前文件；
- 最近更新；
- 已经确定的分图拆解。

只登记已经确认的图片目的和分图内容，不替 04 skill 设计图片。

### 05_论文全周期

固定区分：

- 投前论文成稿；
- 期刊适配；
- 审稿修回。

这里记录真实稿件、各部分进度、投稿材料、投稿状态和逐条审稿意见的推进情况。还没进入的部分保留简短真实状态，不制造稿件版本、期刊或审稿意见。

## 状态写法

只允许以下五种任务状态：

- 待办；
- 进行中；
- 待审计；
- 已完成；
- 取消。

状态写在对应大标题或小标题末尾，格式为“标题｜状态”。不要再单独增加“状态：”字段。

状态含义：

- 待办：已确认需要做，但还没开始。
- 进行中：已经开始但尚未进入审计；资料不足、等待输入或暂时卡住仍属于进行中，并在“卡在哪里”说明。
- 待审计：操作已经完成，但正确性、完整性或可用性还没检查完。
- 已完成：工作和必要检查都完成，可以继续使用。
- 取消：经过明确确认后不再继续。

不能只因为文件存在或有人说“做完了”就标为已完成。

## 大标题状态

大标题状态要概括其内部真实进度：

- 完全没开始时为待办；
- 只要仍有正在推进或暂时卡住的必要事项，通常为进行中；
- 工作已经做完但整体检查未完成时为待审计；
- 必要工作全部完成并检查过后为已完成；
- 只有整个部分被明确放弃时才为取消。

并行推进时，顶部“目前主要做到”可以写多个大部分，不强行假设项目严格按 01 到 05 单线前进。

## 取消和废弃

取消事项不能删除，也不能只留在末尾索引。

在原来的任务块中：

1. 将标题状态改为“取消”；
2. 保留已经完成的过程和结果；
3. 增加取消原因、能否复用和取消时间。

随后在文末“取消 / 废弃记录”增加索引，记录原位置、当时完成程度、原因、相关文件和重启条件。这样既保留现场，也方便集中查找。

## 内容来源和准确性

可以使用：

- 用户明确说过的事实；
- 项目中可读取文件提供的可靠证据；
- 负责对应工作的 skill 已经确认的结果；
- 当前 PROJECT.md 中没有被后续信息否定的记录。

推断必须在写入前明确标为推断并交给用户确认。不得自行发明科学问题、假设、实验安排、分析步骤、图片目的、论文内容、路径或完成状态。

路径应指向真实文件。没有路径就写“还没有”或“无”，不要使用看似真实的假路径。

## 更新一致性

一次状态变化可能需要同时更新：

- 具体任务标题的状态；
- 任务内部的已完成内容、当前位置、下一步、卡点、结果和更新时间；
- 所属大标题状态；
- 顶部“目前主要做到”；
- 顶部“现在在做”；
- 顶部“最近更新时间”；
- 取消事项的原位置和末尾索引。

提出更新方案时必须一次展示这些联动变化。用户只批准其中一部分时，只执行获批部分，并报告因此仍存在的不一致。
