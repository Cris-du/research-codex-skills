# DOCX 工作流

## 总原则

- 用户的自然语言决定本轮是直接写入、仅在会话中讨论，还是先预览后写入。
- 优先使用能够保留现有版式、关系文件、域、批注和修订标记的文档工具。
- 不因技能内部流程机械增加一次确认，也不默认创建 `_working.docx`。
- 修改前识别稿件阶段、目标文件和用户是否要求副本或修订痕迹；信息足够时直接执行。
- 如果当前环境无法以用户要求的方式安全保留复杂版式、域或真实修订，说明具体限制并询问，不得悄悄降级。

## 初稿阶段

以下语义通常表示初稿阶段：用户称文件为“初稿、草稿、第一版”，要求“从零写、先把全文写出来、继续搭正文”，或项目中明确存在正在形成正文的初稿。是否属于初稿由上下文判断，不以文件是否刚创建为唯一标准。

1. 用户要求直接写、继续写或修改时，默认在目标初稿 DOCX 上原位修改。
2. 不创建 `_working.docx`，不默认开启修订模式，也不要求用户为每次修改再确认一次。
3. 用户明确要求“另存一份、别动这个版本、做个备份、存一个版本节点”时，才创建副本或里程碑文件。
4. 用户明确要求“开修订、保留修改痕迹”时，才使用真实 Word 修订。
5. 用户说“先讨论、先给文本、先别写文件”时，只在会话中工作。

新建初稿时，如果目录、文件名和文稿类型都能从请求或项目结构中确定，可直接创建；只有目标不唯一时才询问。后续继续同一初稿，避免人为制造“提纲版、中文初稿、英文版、润色版”等阶段文件。

## 后期稿件与既有稿件

成熟稿件、导师修改稿、投稿稿和返修稿也不采用固定文件策略，而是服从用户本轮表达：

- “直接改这个文件”或等价表达：原位修改目标稿件。
- “在副本上改、保留原稿、另存为……”：创建或使用指定副本。
- “开修订、保留修改痕迹、用 Track Changes”：使用真实 OOXML 修订；新增用 `<w:ins>`，删除用 `<w:del>`。
- “接受修订、清掉批注”属于独立操作，只有用户明确要求时执行。

如果使用修订模式，禁止用字体颜色、下划线、删除线或批注假装修订；也不要用无法保真处理修订的简化方式重存文档。若用户未要求修订模式，则以正常正文编辑完成，同时保留文档中与本轮无关的既有修订和批注。

## 自然语言路由

- 直接执行信号包括但不限于：“直接改”“写进去”“按这个改”“继续写”“替我改好”“你看着处理”。目标和范围清楚时直接写入，不再展示一轮供确认。
- 讨论信号包括但不限于：“先看看”“先分析”“先给方案”“先在会话里写”“不要动文件”。此时不落盘。
- 预览信号包括但不限于：“先给我确认”“先展示改法”“确认后再写”。此时按用户要求等待确认。
- 如果一句话同时包含相反信号，以更具体、更靠近目标文件和动作的要求为准；仍无法判断时只问一个最小澄清问题。
- 图表插入、编号、图注、正文引用和 Zotero 引用遵守同一套路由，不设额外门禁。

以下情况才主动询问：目标文件不唯一；科学含义无法可靠推断；多个 Zotero 候选无法消歧；用户没有授权但操作会大范围删除或重排内容；已有输出与请求发生实质冲突。

## 里程碑

当用户说“存一版”时，从当前活动稿件生成一个有意义且不覆盖既有文件的里程碑，文件名表达语义，例如 `_post-methods-review.docx`。默认继续在用户当前指向的稿件上工作；若措辞指定新版本为后续活动稿件，则切换到新版本。不要为每次小改自动创建版本。

## 验证

写入后按本轮改动范围检查：

1. 重新打开 DOCX，检查包结构、关系文件和目标内容存在。
2. 若本轮要求修订模式，核对修订 XML 数量、作者、时间和修改范围，不把普通文本样式当作修订。
3. 渲染受影响页面；涉及全稿结构、分页、图表或参考文献时渲染完整文档。检查失败时说明未完成的验证，不宣称版式无误。
4. 检查页码、目录、图表、图注、参考文献、分页和字体是否出现与本轮修改有关的异常。
